### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

|**№**|**Требование**|

| 1 | Отклик API истории заказов не должен превышать 1 секунды в 99.99% случаев |
| 2 | Отклик API истории заказов должен быть ≤ 0.3 секунды в 98% случаев |

| 6 | Архитектура должна позволять легко добавлять новые поля в историю заказов без изменения существующих сервисов |

### <a name="_qmphm5d6rvi3"></a>**Решение**

**Выбранный паттерн: CQRS (Command Query Responsibility Segregation) + Event-Driven Architecture**

#### Архитектурное решение

Мы выбрали паттерн **CQRS** с отдельным **Order History Service**, который строит денормализованную read-модель на основе событий от доменных сервисов.

#### Компоненты решения

| Компонент | Технология | Назначение |
|-----------|------------|------------|
| **Order History Service** | Node.js/Go | Построение и обслуживание read-модели истории заказов |
| **Order History DB** | Elasticsearch | Денормализованное хранилище для быстрого поиска и фильтрации |
| **Cache Layer** | Redis | Кэширование частых запросов для достижения SLA |
| **BFF (Backend for Frontend)** | Node.js/Go | Агрегация данных из нескольких сервисов для мобильного клиента |
| **Receipt Service** | Node.js + S3 | Генерация PDF-чеков по событию PaymentProcessed |
| **Review Service** | Node.js + PostgreSQL | Управление отзывами о товарах |

Ссылка на диаграмму C2: [C2.puml](C2.puml)

#### Логика принятия решений

1. **CQRS для разделения нагрузки**: Запросы на чтение истории заказов значительно превышают количество операций записи (соотношение ~10:1). Разделение позволяет оптимизировать каждую сторону независимо.

2. **Денормализация данных**: В read-модель заранее агрегируются данные из Order, Payment, Delivery и Catalog сервисов. Это eliminates необходимость в JOIN across services at query time.

3. **Event-Driven синхронизация**: Order History Service подписывается на события доменных сервисов и обновляет read-модель асинхронно, обеспечивая eventual consistency.

4. **BFF для агрегации на edge**: Для сценариев, требующих данных из нескольких источников (например, "заказать снова" требует данных из Order History + Catalog), BFF выполняет агрегацию ближе к клиенту.

5. **Redis для кэширования**: Горячие данные (последние 10 заказов пользователя) кэшируются в Redis для достижения требования 0.3 сек в 98% случаев.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

#### Альтернатива 1: API Composition

**Описание**: BFF или API Gateway агрегирует данные на лету, делая параллельные запросы к Order, Payment, Delivery и Catalog сервисам.

| Плюсы | Минусы |
|-------|--------|
| ✅ Нет дублирования данных | ❌ Высокая задержка (сумма всех запросов) |
| ✅ Всегда актуальные данные | ❌ Сложность обработки частичных отказов |
| ✅ Проще начальная реализация | ❌ Не масштабируется при росте нагрузки |
| ✅ Нет eventual consistency | ❌ Нарушает требование < 0.3 сек (98%) |

**Почему не выбрали**: При 5-7 параллельных запросах к разным сервисам p99 задержка превысит 1 секунду, что нарушает SLA.

#### Альтернатива 2: Event Sourcing

**Описание**: Хранение всех событий заказа как источника истины, проекция истории заказов строится из потока событий.

| Плюсы | Минусы |
|-------|--------|
| ✅ Полный аудит всех изменений | ❌ Высокая сложность реализации |
| ✅ Возможность重建 состояния из событий | ❌ Требует специализированных инструментов |
| ✅ Идеально для compliance | ❌ Избыточно для данного use case |
| ✅ Гибкие проекции | ❌ Сложность миграции при изменении модели |

**Почему не выбрали**: Event Sourcing добавляет значительную операционную сложность без существенной пользы для данного сценария. CQRS с событиями даёт 80% преимуществ при 20% сложности.

#### Альтернатива 3: Единая база данных для чтения

**Описание**: Order Service пишет в одну PostgreSQL, которая обслуживает и запись, и чтение истории заказов.

| Плюсы | Минусы |
|-------|--------|
| ✅ Простота реализации | ❌ Single point of failure |
| ✅ Strong consistency | ❌ Не масштабируется на 40 000+ заказов/день |
| ✅ Нет дублирования | ❌ Сложные JOIN замедляют запросы |
| ✅ Меньше инфраструктуры | ❌ Нарушает принцип bounded contexts |

**Почему не выбрали**: Не соответствует требованиям масштабируемости и отказоустойчивости микросервисной архитектуры.

### <a name="_xk9m2p4n7q1s"></a>**Недостатки, ограничения, риски**

| Категория | Описание | Митигация |
|-----------|----------|-----------|
| **Eventual Consistency** | Данные в истории заказов могут отставать от источника на 1-5 секунд | Информировать пользователя о возможной задержке; использовать versioning для критичных операций |
| **Дублирование данных** | Данные хранятся в Order DB и Order History DB | Реализовать механизм реконсиляции для исправления расхождений; мониторить lag между системами |
| **Сложность отладки** | Труднее отследить поток данных через события | Внедрить distributed tracing (Jaeger/Zipkin); добавить correlation ID во все события |
| **Обработка ошибок в проекции** | Если Order History Service упадёт, read-модель устареет | Реализовать DLQ для неудачных событий; механизм replay событий из брокера |
| **Миграция схемы** | Изменение структуры событий требует обновления проекции | Версионирование событий; поддержка нескольких версий проекций параллельно |
| **Операционные затраты** | Дополнительный сервис и БД увеличивают стоимость инфраструктуры | Использовать managed сервисы (Elasticsearch Cloud, Redis Cloud); автоскейлинг по нагрузке |
| **Безопасность данных** | Денормализованные данные могут содержать чувствительную информацию | Шифрование PII данных; RBAC на уровне сервиса; аудит доступа к Order History DB |

#### Метрики для мониторинга

| Метрика | Порог | Действие |
|---------|-------|----------|
| Event Processing Lag | > 5 секунд | Alert on-call инженеру |
| API p99 Latency | > 1 секунда | Автоскейлинг Order History Service |
| Cache Hit Ratio | < 80% | Увеличение размера Redis кластера |
| Event Failure Rate | > 0.1% | Проверка DLQ и реконсиляция |
| Data Consistency Check | Расхождения > 0.01% | Запуск jobs для исправления |

#### План внедрения

1. **Фаза 1 (MVP)**: Order History Service с базовой проекцией (OrderCreated, OrderCompleted)
2. **Фаза 2**: Добавление Payment и Delivery событий в проекцию
3. **Фаза 3**: Внедрение Redis кэширования для горячих данных
4. **Фаза 4**: BFF для агрегации сценариев "заказать снова" и отзывов
5. **Фаза 5**: Receipt Service для генерации чеков
